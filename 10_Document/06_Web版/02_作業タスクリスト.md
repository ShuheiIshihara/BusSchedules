## T-03: 日本語正規化のTS移植+単体テスト

**ゴール**: [StringNormalization.swift](../../20_Source/BusNow/BusNow/Utils/StringNormalization.swift) と入出力が完全一致する `src/utils/stringNormalization.ts` がテスト付きで存在する。

`normalizeForSearch` / `normalizeForDisplay` / `normalizeKana` の3関数を実装する。

### 仕様(Swift実装からの正確な移植要件)

1. **Unicode正規化**: `str.normalize('NFC')`(Swiftの `precomposedStringWithCanonicalMapping` 相当)
2. **しんにょう異体字処理**: 対象4文字 `辻`(U+8FBB)・`込`(U+8FBC)・`迫`(U+8FEB)・`追`(U+8FFD) について、**直後に異体字セレクタ U+E0100 が付いていない場合のみ** U+E0100 を付加する。
   - 正規表現: `/(辻|込|迫|追)(?!\u{E0100})/gu` → `'$1\u{E0100}'`
   - ※Swift実装では search用・display用とも同じ「U+E0100付加」処理である(DBデータが異体字セレクタ付きで格納されているため)。この挙動をそのまま踏襲する
3. **空白正規化**: trim → 全角スペース`　`を半角スペースへ → 連続空白を1つに圧縮(`/\s+/g` → `' '`)
4. **処理順序**: normalizeForSearch/Display = ①NFC → ②しんにょう → ③空白。normalizeKana = ①半角カナ→全角カナ・半角英数→全角英数 → ②カタカナ→ひらがな → ③normalizeForSearch を通す
5. **normalizeKana の変換実装**(SwiftはICU transformを使用。JSに標準APIがないため自前実装):
   - 半角カナ→全角: 濁点`ﾞ`(U+FF9E)・半濁点`ﾟ`(U+FF9F)の合成を含むマッピングテーブルで変換(`ｶﾞ`→`ガ` など)。半角英数字も全角へ(`3`→`３`。読みデータが全角数字のため)
   - カタカナ→ひらがな: U+30A1〜U+30F6 の範囲をコードポイント -0x60 シフト

### テスト(Vitest: `src/utils/stringNormalization.test.ts`)

既存の [StopNameRepositoryTests.swift](../../20_Source/BusNow/BusNowTests/StopNameRepositoryTests.swift) のテストケースを移植し、最低限以下をカバーする:

| 入力 | 関数 | 期待値 |
|---|---|---|
| `"辻町"` | normalizeForSearch | `"辻\u{E0100}町"` |
| `"辻\u{E0100}町"`(セレクタ付き) | normalizeForSearch | `"辻\u{E0100}町"`(二重付加しない) |
| `"  名古屋　駅  "` | normalizeForSearch | `"名古屋 駅"` |
| `"ナルミ"` | normalizeKana | `"なるみ"` |
| `"ﾅﾙﾐ"` | normalizeKana | `"なるみ"` |
| `"ｶﾞｰﾃﾞﾝ"` | normalizeKana | `"がーでん"` |
| `"あいかわ1ちょうめ"`(半角数字) | normalizeKana | `"あいかわ１ちょうめ"` |
| `""` | 全関数 | `""` |

**完了条件**: `npm test` が全件パス。

## T-05: Supabaseクライアント+RPCラッパー

**ゴール**: Webから時刻表データが取得できる。

1. `src/services/supabaseClient.ts`:
   ```typescript
   import { createClient } from '@supabase/supabase-js';
   export const supabase = createClient(
     import.meta.env.VITE_SUPABASE_URL,
     import.meta.env.VITE_SUPABASE_ANON_KEY,
   );
   ```
2. `src/services/scheduleApi.ts` に `getBusSchedules(departure, arrival, date)` を実装。iOS版 [SupabaseService.swift:79-186](../../20_Source/BusNow/BusNow/Services/SupabaseService.swift) と同じ振る舞い:
   - 発着名に `normalizeForSearch()` を適用
   - 日付は `YYYY-MM-DD` 形式(ローカルタイムゾーン基準。`toISOString()` はUTCになるため使わないこと)
   - RPC呼び出し:
     ```typescript
     const { data, error } = await supabase.rpc('get_phase1_bus_schedule_3', {
       departure_station: dep,
       arrival_station: arr,
       target_date: dateString,
     });
     ```
   - レスポンスが `null`/`[]` の場合は空配列を返す(エラーにしない)
   - 失敗時は最大3回リトライ(iOS版と同じ)。失敗の種類を表す独自エラー型を定義(接続失敗/空レスポンス/パース失敗)
   - `BusScheduleRPCResponse[]` → `BusScheduleData[]` 変換: 時刻の秒除去(`"06:15:00"` → `"06:15"`)、routeName/destination に `normalizeForDisplay()` 適用、`busStops ?? []`
3. **疎通確認**(実装前に先にやってよい): 
   ```bash
   curl -s "https://{project-ref}.supabase.co/rest/v1/rpc/get_phase1_bus_schedule_3" \
     -H "apikey: {anon key}" -H "Content-Type: application/json" \
     -d '{"departure_station":"{実在停留所名}","arrival_station":"{実在停留所名}","target_date":"2026-07-06"}'
   ```
   実在の発着ペアはiOSアプリの検索履歴か stops.json から選ぶ。

**完了条件**: 実在ペアで `BusScheduleData[]` が返り、コンソールに時刻表が出力される。存在しないペアで空配列が返る。

## T-06: バス停サジェストリポジトリ

**ゴール**: [StopNameRepository.swift](../../20_Source/BusNow/BusNow/Services/StopNameRepository.swift) と同一の候補順序を返す `src/services/stopRepository.ts` がある。

1. `fetch('/data/stops.json')` で初回ロードし、メモリ保持(モジュールスコープのシングルトン+ロードPromiseキャッシュ)
2. ロード時に正規化済みインデックスを構築: `{ stop, name: normalizeForSearch(stop.name), reading: normalizeKana(stop.reading ?? '') }`
3. `suggestions(query: string, limit = 50): Stop[]` を実装。**優先順位はiOSと同一**:
   1. 漢字名 前方一致(`name.startsWith(nameQuery)`)
   2. 読み 前方一致(`reading.startsWith(kanaQuery)`)
   3. 漢字名 部分一致(`name.includes(nameQuery)`)
   4. 読み 部分一致(`reading.includes(kanaQuery)`)
   - 1件のバス停は最初にマッチした階層のみに入れる(iOS実装は else-if 連鎖)
   - `nameQuery` が空なら `[]` を返す
4. Vitestで単体テスト: 注入可能なコンストラクタにし(iOS版と同様)、テスト用の小さい停留所配列で「漢字前方一致が読み前方一致より先に並ぶ」「limitで打ち切られる」「カタカナ・半角カナ入力でヒットする」ことを検証

**完了条件**: `npm test` パス。ブラウザで `suggestions('なごや')` 相当が候補を返す。

## T-09: 時刻表画面

**ゴール**: iOSの `BusScheduleView` 相当の画面が動く。

`src/views/ScheduleView.tsx` を実装。iOS版 [BusScheduleViewModel.swift](../../20_Source/BusNow/BusNow/ViewModels/BusScheduleViewModel.swift) のロジックを踏襲:

1. **ヘッダー**: `"出発 → 到着"`(`normalizeForDisplay` 適用)と現在時刻(HH:MM:SS、`setInterval` 1秒更新。unmount時に `clearInterval`)
2. **データ取得**: 画面表示時に `getBusSchedules()` を呼ぶ。ローディング表示・エラー表示(再試行ボタン付き)を実装
3. **平日/土日祝タブ**: 初期値は当日の曜日から自動判定(土日は「土日祝」。祝日はRPC側のGTFSカレンダーが処理するため、クライアントは日付を渡すだけでよい)。**タブ切替時は次の該当日を自動選択**(平日タブ→次の月曜、土日祝タブ→次の土曜。当日が該当するなら当日)して再取得
4. **日付選択**: `<input type="date">` で任意日付を選択→再取得
5. **行き/帰りトグル**: 発着ペアを反転して再取得
6. **リスト表示**: 各行に発車時刻・路線名・行先・のりば。行タップで経由バス停(`busStops`)を展開表示
7. **時刻演出**(対象日が今日の場合のみ):
   - 発車時刻 < 現在時刻 の行はグレーアウト
   - 現在時刻以降の最初の便をハイライト(次バス)し、初期スクロール位置をそこに合わせる
8. **接近情報ボタン**: 以下URLを**別タブで開く**(`target="_blank" rel="noopener"`。iframe埋め込みはX-Frame-Optionsのため不可):
   ```
   https://www.kotsu.city.nagoya.jp/jp/pc/bus/stand_access.html?name={出発停留所}&toname={到着停留所}
   ```
   停留所名は `encodeURIComponent` でエンコード
9. **戻るボタン**: 停留所選択画面へ

**完了条件**: 実在ペアで時刻表が表示され、タブ・日付・方向の切替で再取得され、過去便グレーアウト+次バスハイライトが現在時刻に追従する。
