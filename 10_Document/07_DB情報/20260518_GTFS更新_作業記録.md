## 投入SQLの仕様

- 1トランザクションで実行し、エラーや検査の失敗があればすべて取り消す。
- 手順: 全列 text の一時テーブルに `\copy` → 9テーブルを TRUNCATE → 型を変換して INSERT → 検査 → COMMIT → ANALYZE
- `routes` → `agency_jp` に外部キーがあるため、まとめて TRUNCATE する。
- `search_history` / `debug_logs` は消さない。
- 型変換
  - `route_id` / `jp_pattern_id` は bigint(先頭の0が落ちる。例: `0001` → `1`)。`trip_id` は元の文字列のまま。
  - 日付は `YYYYMMDD` から date に変換。
- 空欄の扱い(本番データに合わせる)
  - `trips` は `NULL`(RPC が `COALESCE(t.trip_headsign, ...)` を使うため)
  - それ以外の text 列は `''`(translations は主キー列が NOT NULL のため必須)
- 検査内容: 件数がzipと一致、参照切れなし(stop_times→trips / stops、trips→routes / calendar / pattern_jp)、時刻のない便なし、calendar の期間

### 実行方法(リポジトリのルートで)

```bash
unzip -o "10_Document/07_DB情報/20260518_bus-gtfs-jp.zip" -d supabase/seed/gtfs_20260518
psql postgresql://postgres:postgres@127.0.0.1:54322/postgres -v ON_ERROR_STOP=1 -f supabase/snippets/load_gtfs_20260518.sql
```

元に戻すときは `supabase db reset`(本番と同じ状態に戻る)。

## 注意点

- **search_history のキャッシュ**: RPC は同じ検索(日付・出発・到着)が search_history にあると、保存済みの結果を返す。ローカルには本番の履歴が残っているので、新データで確認するときは履歴にない日付を使う。
- **24時以降の時刻**: 新データにも `24:xx` 〜 `26:15` の時刻がある(159件、更新前とほぼ同じ)。RPC 内の `::time` 変換でエラーになる可能性があり、その場合は区間全体が空の結果になる。更新前からある挙動だが、比較では深夜便を含む区間も確認する。
