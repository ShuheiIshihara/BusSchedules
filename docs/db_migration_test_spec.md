# DB移行テスト仕様書(GTFS-JP 20260518版 / ローカルDB)

## 1. 目的・範囲

GTFS-JP 20260518版(feed_version `202603_02`、2026/3/28 ダイヤ改正版)への入れ替えを、本番に反映する前にローカルDBで検証する。
全区間の組み合わせ(約3,900停留所の総当たり)は現実的でないため、**本番で実際によく検索されている区間**を代表サンプルとして使う。

- 対象: ローカル Supabase(`supabase/`)に投入済みの新データ。RPC `get_phase1_bus_schedule_3` の結果と、アプリ側の重複排除。
- 対象外: 本番DBへの書き込み・反映(別途計画)、iOS/Webの画面操作(§8 の手動確認のみ)。
- 背景: [`10_Document/07_DB情報/20260518_GTFS更新_作業記録.md`](../10_Document/07_DB情報/20260518_GTFS更新_作業記録.md)
- 関連: [`docs/supabase_test_spec.md`](supabase_test_spec.md)(通常の動作テスト。本書はそのデータ入れ替え版)

## 2. 変更点とテストの観点

| 変更点 | 影響の見込み | 対応するテスト |
|---|---|---|
| ダイヤ改正(trips 30,713→30,417、stop_times 595,140→592,164) | 便の増減・時刻変更 | M-01〜M-04 |
| サービスID名称変更(`日祝`→`日休`、`日祝メーグル`→`日休メーグル`) | 応答の `serviceId` が変わる。RPC の `weekday`/`other` 判定は `LIKE '%平日%'` のため影響小 | M-03、R-01 |

| 24時以降の時刻(159件) | RPC内の `::time` 変換エラーで区間全体が空になる可能性(更新前からある挙動) | E-01 |
| 異体字セレクタ(U+E0100)を含む停留所名・行先(例: `高辻󠄀`) | 検索一致・表示 | E-02 |
| `search_history` の保持(RPCのキャッシュ) | **同じ日付・区間を再検索するとキャッシュを返し、新データを見ない** | §4.3、P-03 |

## 4. 前提と手順

### 4.1 環境

- ローカル Supabase 起動済み(`supabase start`)。API `http://127.0.0.1:54321`、DB `postgresql://postgres:postgres@127.0.0.1:54322/postgres`。
- **本番には一切アクセスしない**(RPC は呼ぶたびに `search_history` へ書き込むため)。Before も本番のコピーのローカルで取る(`tools/db-compare/README.md` の手順)。
- 鍵・URLを記録に残さない。`LOCAL_ANON_KEY=$(supabase status -o env | sed -n 's/^ANON_KEY="\(.*\)"/\1/p')`

### 4.2 区間・日付の定義

`tools/db-compare/cases.json` を§3.1・§3.2で置き換える(pairs 20件、dates T1〜T4。境界セットは別ファイルまたは追加実行)。

### 4.3 `search_history` のキャッシュに関する注意(重要)

RPC は `(日付, 出発, 到着)` が `search_history` にあると、保存済みの結果を返す。そのため次の2点で誤判定が起きる。

1. 履歴にある日付を使うと、新データではなく本番の古い結果を見てしまう。→ §3.2 の日付は事前に履歴が0件であることを確認する(P-03)。
2. **Before の取得でも履歴が書き込まれる。** そのまま更新SQLを当てて After を取ると、Before の結果が返り、差分0件(偽の合格)になる。→ Before 取得後、更新SQLの適用前または適用後に、テスト日付の履歴を削除する(ローカルのみ)。

```bash
psql postgresql://postgres:postgres@127.0.0.1:54322/postgres -c \
  "delete from search_history where h_target_date in ('2027-03-02','2027-03-06','2027-03-07','2027-03-22','2026-12-31','2027-04-30','2027-05-01')"
```

### 4.4 実施手順

1. `supabase db reset` で本番相当(更新前)に戻す。
2. P-01〜P-03 を確認する。
3. **Before 取得**: `PROD_URL=http://127.0.0.1:54321 PROD_ANON_KEY=$LOCAL_ANON_KEY node fetch.mjs prod`(`tools/db-compare`)
4. §4.3 の `delete from search_history` を実行する。
5. 更新SQLを適用する。
   ```bash
   unzip -o "10_Document/07_DB情報/20260518_bus-gtfs-jp.zip" -d supabase/seed/gtfs_20260518
   psql postgresql://postgres:postgres@127.0.0.1:54322/postgres -v ON_ERROR_STOP=1 -f supabase/snippets/load_gtfs_20260518.sql
   ```
6. **After 取得**: `LOCAL_ANON_KEY=$LOCAL_ANON_KEY node fetch.mjs local && node diff.mjs`
7. §5〜§7 の各検査を行い、§9 の記録に残す。

## 6. 差分の分類(M-03 の判定基準)

Before(更新前)と After(更新後)を比べ、差分を次のどれかに分類する。分類できないものは NG。

| 分類 | 内容 | 判定の方法 |
|---|---|---|
| A. サービスID改称 | `serviceId` が `日祝`→`日休`、`日祝メーグル`→`日休メーグル` に変わっただけ | 比較前に Before 側を機械的に置換して再比較する |
| B. 行先の経由地表記 | `destination` が `X`→`X（…経由）` に変わっただけ | 括弧書きを除いた文字列が Before と一致すれば想定内 |
| C. ダイヤ改正 | 便の追加・削除、時刻・到着時刻・路線名の変更 | 原本照合(O-01)で After が原本と一致していれば想定内。件数の増減は M-04 で確認 |
| D. 停留所の増減による変化 | `busStops` の経由停留所の変更 | 原本照合(O-02)で確認 |
| NG | 上記で説明できない差分(取得エラー、欠落、原本と不一致) | 調査して記録 |

`tools/db-compare/diff.mjs` は完全一致で比較する。分類 A・B は、差分が大量に出てレポートが読みにくくなるため、比較用に正規化してから比較する(A: `日祝`→`日休` を Before に適用、B: `destination` の末尾 `（…経由）` を除去)。この正規化は `diff.mjs` の入力側で行い、生データは変更しない。

## 10. 既知の制約

- 上位20件は実利用に基づくサンプルであり、全区間の網羅ではない。サンプル外の区間・日付での不具合は検出できない。
- 日付は新データの期間内の未検索日に限る。実際に利用者が検索する直近の日付(キャッシュ済み)は対象にできない。本番反映時は、本番の `search_history` の扱い(削除またはその日付範囲の無効化)を決める必要がある(作業記録 残作業)。
- RPC の `ROW_NUMBER() OVER ()` は順序が実行計画に依存するため、同一出発時刻の便の並びは安定しない。比較は順序に依存しない多重集合で行う。
